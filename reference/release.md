# Release pipeline

Two goals: one command produces a signed artifact, and no credential ever
touches git.

## `__secrets/`

A gitignored folder at the repo root holding build-time and publish-time
credentials only. Nothing in it is read at runtime. Client-visible config
(ad unit ids, RevenueCat public keys, the Sentry DSN) belongs in `.env`.

```
__secrets/
  README.md                  Committed. Lists what goes here and where each file comes from.
  upload-keystore.jks        Android upload key.
  keystore.env               Android signing credentials.
  play-service-account.json  Play Console service account, for fastlane supply.
  AuthKey_XXXXXXXX.p8        App Store Connect API key, for iOS upload.
```

`.gitignore` carries `/__secrets/`, `*.jks`, `*.keystore`, and
`/android/key.properties`. The README is the one exception, added with
`!__secrets/README.md`.

## Android signing

Accept two file layouts in `build.gradle.kts` and try them in order:

1. **`keystore.env`** with `ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD`,
   `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. A shared studio-wide credentials
   file can then be dropped in untouched.
2. **`keystore.properties`** with the Gradle-conventional `storeFile`,
   `storePassword`, `keyAlias`, `keyPassword`.

Details that save an afternoon:

- A **blank** key password conventionally means "same as the store password".
  That is how `keytool` behaves when you press enter at its prompt, so fall back
  accordingly.
- Resolve the keystore path against several candidates: absolute, relative to
  the project root, and the bare filename inside `__secrets/`. A shared file
  that moved but was not re-pathed then still resolves.
- When signing config is absent, fall back to debug signing rather than failing
  the build. A contributor without the keystore should still be able to run
  `flutter build apk`.

Create the upload key once:

```bash
keytool -genkey -v -keystore __secrets/upload-keystore.jks \
  -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

Back it up somewhere that is not the laptop. Losing it means you can never
update the app under that listing again without a Play support reset.

## `make android:aab`

The script should:

1. Read the version from `pubspec.yaml`. That file is the single source of
   truth for the store build.
2. On `--submit`, bump the build number (the part after `+`) and write it back.
   Play rejects a duplicate `versionCode` and it is always the thing you forget.
3. `flutter build appbundle --release` with obfuscation and split debug info.
4. Copy the artifact to `dist/<name>_<version>(<build>).aab`, which is the name
   you want when three builds are sitting in the folder.
5. Upload debug symbols to Sentry.
6. On `--submit`, run fastlane supply against the internal test track, passing
   release notes through from `make android:aab:submit NOTES="what changed"`.

## iOS

`make ios:archive` builds and exports; upload with `xcrun altool` or fastlane
`pilot` using the App Store Connect API key from `__secrets/`.

The parts that differ from Android:

- The AdMob app id reaches `Info.plist` through
  `ios/Flutter/Env.xcconfig`, generated by `dart run tool/sync_env.dart`. Run it
  after any `ADMOB_APP_ID_*` change or the build silently ships the previous id.
- `NSUserTrackingUsageDescription` must be present or ATT never prompts.
- The privacy manifest (`PrivacyInfo.xcprivacy`) is required. AdMob and
  RevenueCat both publish theirs; yours declares the required-reason APIs your
  own code uses, usually `UserDefaults`.
- dSYMs go to Sentry, or every release crash report is unreadable.

## Store assets

Keep them in `store/`, generated where possible so a palette change does not
mean an afternoon in an image editor.

```
store/
  listing.md            Title, short description, full description, keywords.
  play-icon-512.png
  feature-graphic.png   1024x500, Play only.
  screenshots/          Captured with `make shots` (ads disabled).
```

Screenshot rules that matter more than they should: the first two are the only
ones most people see, so they carry the hook. Capture at the tallest supported
aspect ratio and let the store letterbox down. Never ship a screenshot with a
banner ad in it.

## Pre-submission checklist

- [ ] `flutter analyze` clean, `flutter test` green.
- [ ] `ADS_TEST_MODE=false`, real ad unit ids, real RevenueCat keys.
- [ ] Version and build number bumped.
- [ ] Debug symbols and dSYMs uploaded to Sentry.
- [ ] A deliberate crash in a release build reached the Sentry dashboard.
- [ ] Purchase and **restore** both tested on a real device, on both stores.
- [ ] `app-ads.txt` live at the developer URL in the listing.
- [ ] Play Data safety form and App Privacy answers match what the SDKs
      actually collect. AdMob and RevenueCat both publish their disclosures;
      copy from those rather than guessing.
- [ ] Content rating questionnaire completed.
- [ ] Target API level meets the current Play requirement.
- [ ] Tested on a low-end device, not just the emulator. A casual game lives or
      dies on cheap hardware.
